# Workflow Rules

## 工作目標

本規範用於專案的需求分析、開發、修改建議、review 與驗證流程。
技術棧：Laravel 12 + Vue 3 (Inertia.js) + Filament 3 + Tailwind CSS

---

## 1. 需求理解流程

### 1.1 先確認需求落點

當使用者提出需求時，先判斷本次修改涉及哪一層：

- **Laravel 後端**：Model、Controller、Migration、Route、Middleware、Form Request
- **Filament 後台**：Resource、RelationManager、Pages、Actions
- **Vue 前端**：Pages、Layouts、Components、Composables
- **CSS / 樣式**：Tailwind class、自訂 CSS、RWD
- **多站台**：Site / SiteSetting / SiteDomain 相關

### 1.2 若需求涉及多層

若需求同時涉及多層，應先列出影響範圍，再分層說明：

- 哪一層需要改
- 各層修改目的
- 是否有相依關係（例如 Model 改了 → Filament Resource 要跟著改）
- 純前端任務派給小前，涉及後端任務派給 executor

---

## 2. 修改建議流程

### 2.1 先沿用既有實作模式

提出修改建議前，優先確認：

- 目前專案是否已有類似的實作方式
- 是否有既有的 Vue 組件、composable 可重用
- 是否有現成的 Filament Resource 模式可參考
- 相同的功能是否有可參考的既有實作

原則上優先延伸既有寫法，不主動引入全新結構或過度重構。

### 2.2 最小影響原則

所有修改建議應以「最小必要變更」為優先：

- 只改本次需求必要範圍
- 不擴大修改無關頁面或元件
- 不因小需求順手重構整段既有邏輯

若需要額外重構，應先明確說明原因與影響範圍。

---

## 3. 回覆與執行方式

### 3.1 先分析，再實作

對於中大型需求，優先採用以下回覆順序：

1. **需求理解**：重述需求，確認理解正確
2. **影響範圍**：列出涉及的檔案（後端 + 前端）
3. **建議修改位置**：指出具體檔案路徑
4. **修改方案**：說明實作方式與注意事項
5. **驗證建議**：提供驗證方式

不要一開始就直接進入程式碼修改，尤其在需求仍有模糊處時。

### 3.2 不確定時先說明假設

若使用者未提供完整資訊，應先清楚說明目前推定的假設，再基於假設提出建議。

---

## 4. 共用元件規則

本專案使用 Vue 3 + Inertia.js 的 Layout 機制：

- 前台共用 Layout：`resources/js/Layouts/SiteLayout.vue`（改一處全站前台生效）
- 後台 Layout：`resources/js/Layouts/AuthenticatedLayout.vue`
- 修改 Layout 時需考慮是否影響所有使用該 Layout 的頁面

---

## 5. 禁止事項

### 5.1 不要擅自擴大修改

禁止因單一需求延伸成大範圍重構，除非使用者明確要求。

### 5.2 不要直接執行危險操作

以下操作需要使用者確認：
- 刪除檔案
- 大量修改多個檔案的結構
- 引入新的外部依賴

### 5.3 不要忽略既有風格

禁止以個人偏好強行改成另一套風格，應優先貼近現有專案寫法。

### 5.4 不要把推測當成事實

若無明確程式碼或需求依據，應標示為推測。

---

## 6. 方案選擇優先級

當多種方案可行時，依以下順序評估：

1. **一致性** — 是否符合專案現有模式
2. **簡潔性** — 是否為最小必要方案
3. **可讀性** — 6 個月後是否能看懂
4. **可維護性** — 之後要改有多難
5. **效能** — 是否有明顯效能問題

---

## 7. 卡住時的處理

同一個問題嘗試 3 次仍失敗時，應停下來：

1. 說明已嘗試的方式與失敗原因
2. 提出 2-3 個替代方向
3. 由使用者決定下一步

不得反覆用相同方式重試。
